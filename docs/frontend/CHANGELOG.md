# API Changelog

Contract changes that affect the frontend. 💥 BREAKING means frontend code must change. See [openapi.json](openapi.json) for the contract snapshot and [error-codes.md](error-codes.md) for error codes.

## 2026-10-29
- New signed-in device management (sign-in required): `GET /api/users/me/sessions` lists every session that can still refresh as `SessionResponse[]` (`sessionId`, `userAgent`, `createdAt`, `lastSeenAt`, `current`, `adminScope`), most recently active first. `userAgent` is the raw User-Agent (parse it on the client); `userAgent`, `createdAt` and `lastSeenAt` are `null` for sessions signed in before this release (show "unknown device"), and `userAgent` / `lastSeenAt` fill in on their next refresh. `lastSeenAt` moves on sign-in and refresh, so it is accurate to about 15 minutes. `DELETE /api/users/me/sessions/{sessionId}` signs out one session (404 `auth.session_not_found` when it is not the caller's or no longer live); signing out the calling session works like logout. `DELETE /api/users/me/sessions?scope=others` signs out every other session; 409 `auth.current_session_unknown` when the access token was issued before this release, so refresh and retry. Both respond 200 `SimpleResultResponse`. New error codes `auth.session_not_found` and `auth.current_session_unknown`.
- Access tokens carry a `sid` claim naming their session. A signed-out session's access tokens stop working on the next request instead of when they expire: protected endpoints answer 401 `auth.session_revoked`, public endpoints serve the request as signed out. The same now happens right away on suspension, role change and refresh-token reuse detection. On `auth.session_revoked` do **not** refresh: clear tokens and go to sign-in, for example with "You were signed out on this device" (see [auth-flow.md](auth-flow.md)). New error code `auth.session_revoked`.

- 💥 New notification `kind` `LIKE`: someone else liked your Comment or Reply. It has `actor` (who liked), `poll` and `comment` (your liked Comment). This is the first place the API names who liked a Comment, and it is intentional: the author sees each liker, likes given before this release included, and follows the same Poll visibility and block rules as `COMMENT`. Unliking removes it, and liking again gives a new, unread one. A client that renders `kind` exhaustively must handle the new value. New preference switch `likes` (default `true`) in `GET` / `PATCH /api/users/me/notification-preferences`. Deploy: Flyway `V10__mark_existing_likes_read.sql` marks every existing like read, so badges do not jump.
- Notifications add `category`, fixed by `kind`: `CONVERSATION` (`COMMENT`, `MENTION`), `LIKE` (`LIKE`), `POLL_END` (`RESULT`, `CANCELLED`, `CLOSING_SOON`), `INVITATION` (`INVITATION`) and `FOLLOW` (`FOLLOWED`). `GET /api/notifications` and `GET /api/notifications/unread-count` take an optional `category` that returns only that tab's items or count. Keep the same `category` while paging. An unknown value is 400 `common.type_mismatch`. `POST /api/notifications/read-all` still reads every category.

## 2026-10-28

- 💥 Blocks now also work the other way for Polls. When a user blocks someone, every Poll the blocker created becomes unreachable for the blocked user, Invite-only Polls they are invited to included: `GET /api/votes/{voteId}` and every other `/api/votes/{voteId}/**` endpoint (results, voters, casting or retracting a Ballot, my-vote-status, share, Comments and Replies: list, post, edit, delete, like, unlike, report) respond 404 `vote.not_found`, and so does marking a notification read by such a Poll's id. The only exception is `GET /api/votes/{voteId}/creator`, which still names the owner. Those Polls leave the blocked user's `GET /api/votes` (Feed / Explore / Search / Top), `GET /api/votes/following` and `GET /api/votes/my`, and the blocker's `GET /api/users/{username}/votes` is empty for them (`totalPolls` on the profile still counts the Polls). `GET /api/notifications` and `/unread-count` no longer list or count anything about those Polls (`RESULT` and `COMMENT` included). The blocker sees everything as before. Nothing is deleted: the blocked user's earlier Ballots still count toward Turnout and option counts, and unblocking restores everything. Follower and following lists and counts are still not filtered by blocks. Block-dialog copy that says the blocked user still sees your content must change.
- `GET /api/notifications` and `/unread-count`: a Reply in a thread started by a user you blocked no longer gives a `COMMENT` notification, matching the Comment lists, which hide that whole thread.
- OpenAPI only: `VoteResponse.myBallotAnonymous` no longer says it is null whenever `myOptionId` is null. It is null only without a Ballot; a sealed Anonymous Ballot of an Ended Poll has `myOptionId` null and `myBallotAnonymous` `true` (behavior unchanged since 2026-10-23).
- OpenAPI only: the `PATCH /api/users/me` description no longer says the response is masked like the public profile. Fields you explicitly hid are `null`; fields whose visibility you never set are shown (behavior unchanged).
- New `POST /api/votes/{voteId}/report` (sign-in required): report a Poll to the moderators. Body `{ "reason": "SPAM" | "HARASSMENT" | "HATE" | "MISINFORMATION" | "OTHER", "note"?: string }` (`note` up to 500 characters; blank is stored as none), same shape as the Comment report. 200 `SimpleResultResponse`. Idempotent per user and Poll: a repeat report succeeds and keeps the first one. Any Poll the caller can reach (Scheduled, Open or Ended). Errors: 400 `vote.report.self` (own Poll; hide the action there), 400 `common.validation_failed` (`reason` missing, `note` too long), 400 `common.bad_request` (unknown `reason`), 404 `vote.not_found` (Deleted or unreachable Poll, including one whose owner blocked the caller), 404 `user.not_found`. New error code `vote.report.self`.
- New `GET /api/admin/vote-reports?page=&limit=` (role ADMIN): offset page of Poll reports, newest first, each with `voteId`, `voteTitle`, `voteDeleted`, `ownerId`, `ownerUsername`, `reporterId`, `reporterUsername`, `reason`, `note`, `createdAt`; same paging as `GET /api/admin/comment-reports`. Deploy: Flyway `V6__vote_reports.sql` adds `vote_reports` at startup.
- New `PUT /api/votes/{voteId}/bookmark` and `DELETE /api/votes/{voteId}/bookmark` (sign-in required): bookmark a Poll the caller can reach, in any state, or remove the bookmark. Both idempotent and return 200 `SimpleResultResponse`; a repeat bookmark keeps its first time and place in the list. `PUT` errors: 404 `vote.not_found` (Deleted or unreachable Poll), 404 `user.not_found`. `DELETE` always succeeds, also for a Poll the caller can no longer reach.
- New `GET /api/votes/bookmarked` (sign-in required): cursor-paged bookmarked Polls, most recently bookmarked first, any state and Audience; Deleted Polls, Invite-only Polls the caller was removed from and Polls whose owner blocked the caller are left out. Errors: 400 `common.cursor_invalid`.
- Poll responses (`GET /api/votes/{voteId}`, lists, My Polls, profile) add `bookmarked`: whether the signed-in caller bookmarked the Poll; null when signed out and in admin views.
- `GET /api/notifications`: `RESULT` now also reaches users who bookmarked the Poll before it Ended (not Invite-only Polls they are no longer invited to); bookmarking an already Ended Poll gives none. Still one `RESULT` per Poll with the same `id` (`result_<pollId>`), so a user who voted in and bookmarked a Poll sees it once, and its read state is unchanged. Removing the bookmark removes the `RESULT` unless the user also owns, voted in or is invited to the Poll. Deploy: Flyway `V7__vote_bookmarks.sql` adds `vote_bookmarks` at startup.
- `GET /api/users/me/export` adds `bookmarks` (`{ voteId, createdAt }`, oldest first).
- New notification kind `MENTION` in `GET /api/notifications` and `GET /api/notifications/unread-count`: someone else wrote `@<username>` (a username, 3-50 characters of `[a-z0-9_]`, case-insensitive, not preceded by a letter or digit of any script or `_`; at most 10 distinct users per Comment, the first handles in the text) in a Comment or Reply on a Poll you can see. Same shape as `COMMENT` (`actor` = author, `poll`, `comment`); id `mention_<commentId>`. A Comment that gives you a `COMMENT` gives no `MENTION` (a Reply under your deleted Comment gives no `COMMENT`, so it is a `MENTION`), unless you switched `comments` off; `POST /api/notifications/{id}/read` with such a `mention_` id responds 404 `notification.not_found`. An edit can only remove mentions: it never notifies a user the original text did not mention. Clients that switch on `kind` must handle the new value.
- `GET` / `PATCH /api/users/me/notification-preferences` add switch `mentions` (default `true`).
- `POST /api/votes/{voteId}/comments` and `PUT /api/votes/{voteId}/comments/{commentId}`: no request change; mentions are parsed from `text`. Deploy: Flyway `V8__comment_mentions.sql` adds `vote_comments.mentioned_user_ids` at startup; Comments written before it mention nobody. Admin: the per-Comment limit is the `config` lookup `comment_max_mentions` (default 10); handles past it are plain text, not an error.
- New `PUT /api/tags/{tagId}/follow` and `DELETE /api/tags/{tagId}/follow` (sign-in required): follow or unfollow a tag; both respond 200 `SimpleResultResponse` and are idempotent. Errors: 400 `common.bad_request` (`tagId` not a valid id); `PUT` also 404 `tag.not_found` and 404 `user.not_found`, while `DELETE` succeeds for an unknown tag. New `GET /api/tags/following` (sign-in required; 401 when signed out): the caller's followed tags as `TagDto[]`, most recently followed first, not paginated (`[]` when none). Deploy: Flyway `V9__tag_follows.sql` adds `tag_follows` at startup.
- `GET /api/votes/following` now also lists Open PUBLIC Polls carrying a tag the caller follows, from any user; a Poll matching both a followed user and a followed tag (or several followed tags) appears once. Order and cursor are unchanged. The list now also leaves out the caller's own Polls and Polls of suspended users; before, a followed user who was later suspended still showed.
- `GET /api/users/me/export` adds `followedTags` (`{ tagId, createdAt }`, oldest first). A followed tag never raises `CLOSING_SOON`, which stays limited to followed users.
- Any signed-in write (every method but `GET`, `HEAD` and `OPTIONS`, outside the public auth endpoints such as sign-in, `/api/auth/refresh` and `/api/auth/logout`) by an account deleted after its access token was issued now responds 404 `user.not_found` before reaching the endpoint, as a suspended account already gets 403 `auth.account_banned`. Idempotent removals such as `DELETE /api/votes/{voteId}/comments/{commentId}/like` used to succeed for such an account. Passkey registration (`POST /api/auth/passkey/register/options` and `/verify`) is now checked too: a suspended account gets 403 `auth.account_banned`, a deleted one 404 `user.not_found`.
- `/api/admin/**` decides every call by a token with the admin role, reads and writes alike, by the account in the database: deleted after its access token was issued 404 `user.not_found` (was 403 `common.forbidden` for a read), suspended 403 `auth.account_banned`, no longer an admin 403 `common.forbidden`. A token without the admin role still gets 403 `common.forbidden`, reads and writes alike, whatever the account's state (a write by a deleted account was 404 `user.not_found`).
- OpenAPI only: the API description lists the filter-level 404 `user.not_found` next to 401/403/429.
- `GET /api/notifications` and `/unread-count`: a Comment read as `COMMENT` stays read when switching `comments` off lists it as `MENTION`, and the other way round; read state is shared by the two kinds for the same Comment.

## 2026-10-27

- New `POST /api/auth/admin/passkey/login/verify` (public, rate-limited like `/api/auth/admin/verify-otp`): the admin console's passkey sign-in. Get the challenge from `POST /api/auth/passkey/login/options`, send `{ "credential": <credential.toJSON()> }`; responds like `POST /api/auth/admin/verify-otp` with tokens that grant the admin role. A passkey whose owner is not an admin gets 403 `auth.admin.forbidden` (the same response `/admin/verify-otp` gives a non-admin); a suspended admin 403 `auth.account_banned`; a rejected passkey 401 `auth.passkey.invalid`. `POST /api/auth/passkey/login/verify` never grants the admin role, also for an admin.

- New `POST /api/auth/passkey/login/options` and `POST /api/auth/passkey/login/verify` (public, no token; rate-limited with the other `/api/auth/**` endpoints): usernameless passkey sign-in. `login/options` returns `PublicKeyCredentialRequestOptionsJSON` `{ challenge, timeout, rpId, allowCredentials: [], userVerification: "preferred" }` for `PublicKeyCredential.parseRequestOptionsFromJSON` / `navigator.credentials.get`; the challenge is single-use and expires after 5 minutes. `login/verify` takes `{ "credential": <credential.toJSON()> }` and responds like `POST /api/auth/verify-otp` (`AuthResponse` with `token`, `refreshToken`, `user`; `isNewUser` always `false`); its tokens never grant the admin role. Errors: 401 `auth.passkey.invalid` (unknown passkey, wrong signature, origin or RP ID, unknown, spent or expired challenge, malformed response), 403 `auth.account_banned`, 400 `common.validation_failed`. A sign count that did not increase is logged, not rejected.
- New `GET /api/users/me/passkeys` (sign-in required; 401 when signed out): the caller's passkeys, oldest first, as `PasskeyResponse[]` `{ id, name, createdAt, lastUsedAt, transports }` (`[]` when none; never key material). New `DELETE /api/users/me/passkeys/{passkeyId}` (sign-in required): removes one of the caller's passkeys, responds 200 `SimpleResultResponse`, written to the audit log (action `DELETE`, resource `PASSKEY`). Errors: 400 `common.type_mismatch` (`passkeyId` not a UUID), 404 `common.not_found` (unknown id or another user's passkey). `PasskeyResponse`, including the `POST /api/auth/passkey/register/verify` response, adds `transports` (AuthenticatorTransport values such as `internal`, `hybrid`; `[]` when the browser reported none).

- New `POST /api/auth/passkey/register/verify` (sign-in required; 401 when signed out): body `{ "credential": <credential.toJSON()>, "name": "iPhone" }` (`name` optional, at most 100 characters), responds 200 `PasskeyResponse` `{ id, name, createdAt, lastUsedAt }`. The server checks the challenge from `/register/options` (single-use: it is spent even when verification fails, so a retry needs new options), the origin (`https://vomatt.com`, `https://admin.vomatt.com`), the RP ID and the key algorithm. Errors: 400 `auth.passkey.invalid` (malformed, wrong origin or RP ID, unknown, spent, expired or another user's challenge), 400 `common.validation_failed` (`credential` fields missing, `name` too long), 404 `user.not_found`, 409 `common.conflict` (passkey already registered). New error code `auth.passkey.invalid`.

- New `POST /api/auth/passkey/register/options` (sign-in required; 401 when signed out): returns WebAuthn creation options (`PublicKeyCredentialCreationOptionsJSON`; pass `data` to `PublicKeyCredential.parseCreationOptionsFromJSON`, then `navigator.credentials.create`). `rp.id` is always `vomatt.com`, `authenticatorSelection` is `{ residentKey: "required", requireResidentKey: true, userVerification: "preferred" }`, `attestation` is `none`, `pubKeyCredParams` are ES256 (-7) and RS256 (-257), `hints` sits at the top level, and `excludeCredentials` lists the caller's existing passkeys (`[]` when none). Binary fields are base64url without padding. The challenge is single-use and expires after 5 minutes. Errors: 404 `user.not_found` (account deleted). Deploy: Flyway `V5__passkey_credentials.sql` adds `passkey_credentials` at startup; `PASSKEY_RP_ID` (default `vomatt.com`) and `PASSKEY_ALLOWED_ORIGINS` (default `https://vomatt.com,https://admin.vomatt.com`) configure the RP.

- `DELETE /api/votes/{voteId}/comments/{commentId}/like`: two unlikes from the same user at the same moment now both succeed. Before, the second could fail with 500.
- `POST /api/votes/{voteId}/comments/{commentId}/like`: liking a Comment that is deleted at the same moment now responds 404 `comment.not_found` and keeps no like. Before, a hard delete gave 500 and a soft delete left a like on the deleted Comment.
- `POST /api/votes/{voteId}/comments/{commentId}/report`: a signed-in user whose account was deleted now gets 404 `user.not_found`. Before, it was 500. Reporting a Comment that is deleted at the same moment now responds 404 `comment.not_found` and keeps no report. Before, a hard delete gave 500 and a soft delete kept a report on the deleted Comment.
- `POST /api/votes/{voteId}/comments/{commentId}/like`, `POST /api/votes/{voteId}/comments/{commentId}/report` and `POST /api/votes/{voteId}/comments` with a `parentId` now respond 404 `comment.not_found` for a Comment the lists hide from the caller: one written by a user the caller blocked, or a Reply in a thread such a user started. Before, knowing the id was enough to like, report or reply to it. `DELETE .../like` is not affected, so a like given before the block can still be taken back. A block by the author alone does not hide their Comments, as in the lists.
- `PUT /api/votes/{voteId}/comments/{commentId}`: the response's `likedByCurrentUser` now reflects the caller's like. Before, it was always `false`, so editing a Comment you had liked showed it as not liked until the next read.
- `POST /api/votes/{voteId}/comments/{commentId}/like`: two likes from the same user at the same moment (e.g. a double tap) now both succeed with one like kept. Before, the second could fail with 500.
- 💥 `POST /api/auth/line`: when LINE rejects the code, the access token or the id_token (4xx), the response is now 401 `auth.line.token_exchange_failed` / `auth.line.profile_failed`; when LINE fails (5xx), rate limits (429 / 408) or does not answer in time, it is 503 `common.service_unavailable`. Both used to be a generic 500. On 503 don't resend the same request: the LINE authorization code is single-use and may already be spent, so restart LINE Login to get a new code. When LINE returns an id_token, the login now requires LINE's verify result: a rejected id_token (4xx), an unusable one or one that belongs to another LINE user than the profile is 401 `auth.line.token_exchange_failed`, and a verify failure (5xx, 429 / 408, no answer, or an empty or malformed body) is 503. The login no longer falls back to the synthetic `line_<userId>@line.oauth` email in those cases, which could create a second account for a user who already has one; the synthetic email is used only when LINE returns no id_token, or verifies it but returns no email.

- `GET /api/votes/{voteId}` now counts a View when the caller is signed in, not the Poll's owner, and the Poll is Open and PUBLIC, at most once per user and Poll per 24 hours (input for a future Trending list; not exposed in any response). No client change: the response and errors are unchanged, and the View is counted asynchronously, so it never fails or slows the request. Deploy: Flyway `V4__vote_view_hours.sql` adds `vote_view_hours` at startup.

- New `POST /api/votes/{voteId}/share` (sign-in required): call it after the user shared the Poll's link with the share button. Body `{ "channel": "COPY_LINK" | "NATIVE" | "LINE" | "FACEBOOK" | "X" | "THREADS" | "OTHER" }` (`NATIVE` is the system share sheet, e.g. `navigator.share`), responds 200 `{ "shareCount": 18 }`. Idempotent per user and Poll: a repeat share succeeds, keeps the first `channel` and leaves the count unchanged. Any Poll the caller can reach counts, Scheduled and Ended included. Errors: 400 `common.validation_failed` (`channel` missing), 400 `common.bad_request` (unknown `channel`), 404 `vote.not_found` (Deleted or unreachable Poll). Signed-out viewers can still share the link but are not counted, so don't call it (it would be 401).
- Poll responses (`GET /api/votes/{voteId}`, lists, My Polls, profile, admin) add `shareCount`: distinct users who shared the Poll, always present (`0` when none). Deploy: Flyway `V3__vote_shares.sql` adds `vote_shares` at startup.

## 2026-10-26

- `POST /api/auth/refresh`: the grace window no longer returns the pair once that sign-in has been logged out, ended by reuse detection or revoked (suspend, role change, account deletion); such a request gets 401 `auth.refresh_token.invalid`. `POST /api/auth/logout` with a refresh token that was already refreshed now signs out that sign-in: the token that replaced it gets 401 `auth.refresh_token.invalid`. `X-Client-IP` is now normalized (one spelling per address), so IPv6 and IPv4-mapped forms share one rate limit. Deploy: `CLIENT_IP_SECRET` is now required in production; the API refuses to start without it.
- New `POST /api/votes/{voteId}/comments/{commentId}/report` (sign-in required): body `{ "reason": "SPAM" | "HARASSMENT" | "HATE" | "MISINFORMATION" | "OTHER", "note": "..." }` (`note` optional, max 500 characters), responds 200 `SimpleResultResponse`. Idempotent per user and Comment: a repeat succeeds and keeps the first report. Errors: 400 `comment.report.self` (your own Comment), 400 `common.validation_failed` (`reason` missing, `note` too long), 400 `common.bad_request` (unknown `reason`), 404 `comment.not_found` (deleted or unknown Comment), 404 `vote.not_found` (Deleted or unreachable Poll). Admin: new `GET /api/admin/comment-reports` (offset-paged, newest first; items `{ id, commentId, voteId, parentId, commentText, commentDeleted, authorId, authorUsername, reporterId, reporterUsername, reason, note, createdAt }`), recorded in the audit log (action `VIEW`, resource `COMMENT_REPORT`). Deploy: run `schema.sql` (adds `comment_reports`).
- OpenAPI only: `POST /api/users/me/follows/{userId}` no longer says the followed user is not told. Since the notification feed, they get a `FOLLOWED` notification (it vanishes if the follow is undone); the 2026-10-24 entry's "not told" no longer holds.
- `GET /api/votes/{voteId}/comments` items add `replies` (the first 2 visible Replies, oldest first, filtered like `/replies`: no deleted Replies, none by users the caller blocked) and `repliesNextCursor` (pass it as `cursor` to `GET /api/votes/{voteId}/comments/{commentId}/replies` to load the rest without repeating the previews; `null` when `replies` already holds all `replyCount` Replies). Both are always present: `replies` is `[]` and `repliesNextCursor` `null` on Replies, on single-Comment responses and on create / update responses.
- `GET /api/notifications` items carry what a row needs, so no per-row fetch of the Poll or profile is needed. `poll` adds `startTime`, `myOptionId` (the caller's Ballot option; `null` without a Ballot or once an Anonymous Ballot of an Ended Poll is sealed), and once the Poll has Ended `winningOptionIds` / `winningOptionLabels` (the option(s) with the most Ballots, display order; `[]` when no Ballot named an option) and `tie` (`true` when several share the most). All three are `null` until the Poll has Ended; `poll` still carries no per-option counts. `actor` is now `FollowUserDto`: the same fields plus `isFollowing` and `followsYou`. `comment` adds `parentId` (the Comment a Reply is under; `null` for a top-level Comment).
- New `GET /api/users/{username}/mutual-followers` (sign-in required; 401 when signed out): the user's followers whom the caller follows ("Followed by @jtan and 2 others you follow"), in follower list order (most recently followed the user first), cursor-paged like `/followers`, items `FollowUserDto` (`isFollowing` always `true`). Suspended users and users with a block between them and the caller, in either direction, are left out. Empty on the caller's own profile. An unknown or suspended `username` is 404 `user.not_found`; a cursor from another list or user is 400 `common.cursor_invalid`.
- `GET /api/users/{username}` adds `mutualFollowersCount` (the length of that list) and `mutualFollowersPreview` (its first 3 items as `UserDto`: `id`, `username`, `displayName`, `avatarUrl`; `[]` when there are none). Both are `null` when signed out and on the caller's own profile, and `null` in the `PATCH /api/users/me` response.
- `GET /api/users/{username}` adds `followersCount` and `followingCount` (always present) and `followsYou` (whether the user follows the caller; `null` when signed out, `false` on the caller's own profile, like `isFollowing`). `GET /api/users/me` (and the `profile` of `GET /api/users/me/export`) adds `followersCount` and `followingCount`; the `PATCH /api/users/me` response carries all three (`followsYou` `false`). The counts match the `GET /api/users/{username}/followers` / `/following` lists: suspended accounts are left out, blocks do not filter them.
- Items of `GET /api/users/{username}/followers`, `GET /api/users/{username}/following` and `GET /api/users/me/follows` add `isFollowing` (the caller follows the user) and `followsYou` (the user follows the caller), both booleans, never `null` (these lists require sign-in), and `false` on the caller's own entry. The other item fields are unchanged; the item schema is now `FollowUserDto` instead of `UserDto`.
- New notification feed `GET /api/notifications` (sign-in required): the caller's notifications, newest first, cursor-paged like other lists. Items are `{ id, kind, createdAt, read, actor, poll, comment }`; `kind` is `RESULT` (a Poll you own, voted in or are invited to Ended), `CANCELLED` (an Invite-only Poll you are invited to was Cancelled before it opened; only Polls Cancelled before 2026-10-14), `INVITATION` (invited to a Scheduled or Open Invite-only Poll; replaced by `RESULT` once it Ends), `FOLLOWED` (someone followed you; one item per follower, group them in the UI), `COMMENT` (someone else commented on your Poll or replied to your Comment; `comment.excerpt` is at most 120 characters plus "…") or `CLOSING_SOON` (a Poll you are invited to, or a Public Poll of someone you follow, ends within 24 hours and you hold no Ballot). `actor` is a user summary like `GET /api/users/search` items (null for `RESULT`); `poll` is `{ id, title, endTime, status, turnout }` with no per-option counts (null for `FOLLOWED`). Nothing from suspended users or from users you blocked or who blocked you is listed. Items are derived when read, so one vanishes when its source goes (Comment deleted, follow undone, Poll Deleted). See [notifications](flows/notifications.md).
- New `POST /api/notifications/{id}/read` takes the feed's notification `id` (e.g. `comment_0199…`), and new `POST /api/notifications/read-all` marks everything up to now read (later notifications arrive unread). Passing a Poll id to `POST /api/notifications/{id}/read` is deprecated but keeps working as before (reads the Poll's Invitation while it is not Ended, its Result after). A malformed id is now 404 `notification.not_found` (was 400 `common.bad_request`).
- `GET /api/notifications/unread-count` now counts every kind in the feed: follows and Comments raise the badge too, and Invitations from users you blocked or who blocked you no longer count.
- New `GET` / `PATCH /api/users/me/notification-preferences`: `{ resultsIn, invitations, comments, closingSoon }`, defaults `true`, `true`, `true`, `false`. `PATCH` sets the fields sent (omitted or `null` keeps the value) and returns all four. A kind switched off (`resultsIn` covers `RESULT` and `CANCELLED`) is left out of the feed and the unread count; `FOLLOWED` has no switch. There is no push or email channel. The switches also appear under `preferences` in `GET /api/users/me/export` (`notifications.<field>`).
- Deploy: before releasing the API, run `db/migrations/2026-10-26-notification-reads-by-kind.sql` and `schema.sql` (either order; adds `notification_read_all` and `idx_votes_creator_end`). Read state carries over: a Poll read before it Ended keeps its Invitation read, one read after keeps its Result read.
